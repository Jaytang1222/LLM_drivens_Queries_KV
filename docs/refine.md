# KART 高级索引与 CBO 对比优化记录

> 更新日期：2026-10-15
> 范围：记录围绕“E2E 超越 CBO、提高高级索引执行效率并降低规划时间、改善 TShape（TS）支持”所做的代码工作、轻量诊断结果和当前限制。本文不把诊断 pilot 写成正式基准结论。

## 1. 结论摘要

目前实现已经可以生成并选择 TS 计划，并对 XZ、TShape、XZT 的范围扫描做了基于 posting 分布的范围合并；在一条 TShape 查询上，合并扫描范围后结果仍与冻结的 FullScan Oracle 一致。有限诊断也显示 TS 计划可进入候选集。

但三个目标都尚未完整解决：

1. **KART E2E 稳定胜过 CBO 和其他方法：未证明。**最新计划诊断没有执行查询；TShape 微基准只有一个查询且不含规划时间。较早的 12 查询 pilot 虽有 KART/CBO E2E p50 数据，但高级索引配置和缓存状态不够可靠，不能作为公平胜出的证据。
2. **高级索引执行优于 CBO，且规划降至 100 ms 以下：未解决。**TS 范围任务数减少了 8 倍，索引阶段中位数下降；但整体执行时间的均值仅下降约 0.9%，波动较大。计划时间仍约 0.5–0.6 秒，单查询中 KART 的计划时间还高于 CBO。
3. **TS 支持：取得了可验证的局部进展，但泛化和性能优势未证明。**12 条 plan-only 查询中 3 条选出 `P_TS`；强制执行的一条 TS 查询通过 Oracle，但不能据此推断其他查询或全量 E2E。

本轮计划诊断均使用 `--policy=rule`，**没有调用 LLM**。因此这些结果验证的是候选生成、代价排序、编译、执行和计量路径，不构成 LLM 贡献的证据。

## 2. 本轮针对性代码工作

### 2.1 高级索引候选与计划选择

- 增加按查询时间跨度和空间谓词形状路由高级候选的逻辑：较长时间窗偏向 XZ，较短时空窗偏向 XZT 组合，中间情况保留有限的 XZ/XZT 候选；路由最多注入两个高级候选模板，控制候选扩张。
- 在 Final 选择中加入高级计划代价代理：利用计划特征中的精确 posting 估计、合并扫描 posting、扫描范围数以及并发分支成本，只有估计超过安全经典候选的设定收益余量时才采纳高级计划；低成本经典查询不会仅因有高级候选而被强制切换。
- BeamSearch 对高级候选采用有限 shortlist，优先保留经典安全候选和代价较低的高级候选，减少验证与最终代价提取的工作量。
- 当前规则默认把时间跨度至少 12 小时的查询归入长窗路由，把小于 6 小时且有空间条件的查询归入短窗路由；高级 Final gate 默认要求最佳非 FullScan 经典候选估计至少 8 秒，且高级代理成本比它低至少 5%。这些是当前代码默认阈值，不是本轮从 holdout 学得的阈值。
- 高级分支执行代理目前使用固定系数估计合并 posting、精确 posting 和范围开销；组合分支按并发执行取较慢分支估计。它是筛选用 proxy，不是已经验证准确的实际执行时间预测器。
- 这些机制以规则和代价代理运行；本轮未证明该代理能稳定预测实测执行赢家，也未证明其带来 E2E 净收益。

### 2.2 XZ、TS、XZT 的范围生成与精确过滤

- 新增 `CodeRangeBudget`：合并重叠或相邻的 SFC 编码范围；当物理扫描范围超过预算时，按相邻范围之间的 gap cost 合并，支持用快照 posting 直方图估计 gap 内额外 postings，而不只按编码长度排序。
- XZ、TS 和 XZT 适配器保留原始精确码范围作为过滤集合，物理扫描可以使用合并后的较粗范围；扫描返回后再按精确码范围过滤 posting，从而把范围合并引入的额外读取限制为假阳性，避免把范围间 gap 的 posting 当成命中候选。
- TS 增加可选环境变量 `KART_TSHAPE_MAX_RANGES`。它只能降低 plan/layout 请求的范围数上限，不会放大原预算；未设置时沿用默认布局上限 64。
- 查询级 posting 统计区分合并前的 `postings_raw` 和精确码过滤后的 `postings_after_code_filter`。

### 2.3 实验隔离和计量

- 结果中记录 `advanced_indexes_enabled`，并记录 TS 范围上限等运行元数据，便于查明某个 arm 实际可用的索引集合。
- 将实际发出的 ScanTask 数 `emitted_ranges` 与客户端操作估计 `client_ops` 分开计量，避免把范围任务数误解为 RPC 数。
- `t_plan_ms`、`t_exec_ms` 和计划 regret 有独立字段；plan-only 不填执行时间，suite 元数据记录范围配置。
- 本轮本地 Maven 聚焦测试开始时发现 `Coordinator.fullScan` 留有已删除 helper `noteEmittedRanges` 的调用。由于节点计量现在会从 PhysicalPlan 统计扫描任务，该调用冗余且导致编译失败；已移除残留调用，随后 60 项聚焦测试全部通过。

### 2.4 当前对比臂配置的重要说明

当前 `NativePolicyArm` 对 arm id 为 `cbo` 的查询明确关闭高级索引；其他原生臂在 `KART_ADVANCED_INDEXES=1` 时可以启用高级索引，运行结果同时记录实际开关。因此当前配置表达的是“经典索引 CBO”与“可使用高级索引的 KART 系统”的系统级比较，不是两种规划器在完全相同物理候选菜单上的纯算法比较。

当前 `experiments/suites/e2e-adv-complex-diagnostic.yaml` 注释写着 CBO 与 KART 使用相同高级索引菜单，但这与 `NativePolicyArm` 的实际代码不一致。阅读或复跑该 suite 时应以 arm 实际输出的 `advanced_indexes_enabled` 为准；在进行可发表或正式胜负判断前，应明确选择系统级菜单比较或同菜单规划器比较，并同步 suite 注释和配置。共享的特征提取、代价和搜索代码也可能影响 CBO 路径，所以结果还必须绑定代码提交和配置快照。

`AdvGoldPlans` 与 `config/adv_gold_plans_v1.json` 是工作区中的旁路材料；当前源码没有发现运行路径调用它们，本轮结果不依赖该 gold 映射。在线收益拟合文件 `config/online_benefit_model_adv_v1.json` 也标注为 census side-track；本轮诊断未使用它。不能把这些文件当成本轮胜因或无泄漏验证结果。

## 3. 轻量实验配置与结果

### 3.1 12 条查询的 plan-only 机制诊断

- 工作负载：`experiments/workloads/bound_ir_adv_complex_diag_v1.json`，manifest `tdrive_v1_ready`，绑定冻结 Oracle `experiments/workloads/bound_ir_adv_complex_diag_v1.oracle.json`。
- 服务器诊断目录：`/home/tyq/projects/llm-kv-advdiag-20261014/experiments/tmp/ts-range-cap-check-20261015/`；12 条 plan-only 结果文件为 `plan12-cap8-cap3.jsonl`。
- 规模：12 条查询、9 类查询形状；选择种子 `20261014`。数据文件声明以种子打乱可用轨迹、尽量使用不同车辆和粗空间单元，并且没有依据任一方法的胜负挑选样本。它是机制诊断集，不是总体分布估计。
- Oracle 元数据：T-Drive 快照 47,102 条轨迹，12 条查询均有非空答案，其中 3 条是 Top-K；来源标为 `FullScanOracle`。
- 策略：`rule`，plan-only，不执行查询、不调用 LLM；分别采用验证候选上限 5 和 3。

| 验证候选上限 | 高级计划数 | 其中 TS | 其他高级计划 | 计划时间中位数 | 计划时间均值 |
|---:|---:|---:|---:|---:|---:|
| 5 | 4/12 | `P_TS` 3 条 | `P_XZTXZ` 1 条 | 555 ms | 579 ms |
| 3 | 4/12 | `P_TS` 3 条 | `P_XZTXZ` 1 条 | 507.5 ms | 约 540.7 ms |

把候选上限从 5 降至 3 后，计划时间中位数下降 47.5 ms（约 8.6%），均值下降约 38.3 ms（约 6.6%），但仍远高于 100 ms 目标。高级计划选中数量没有变化；有一个空间查询从 `P_Z` 变为 `P_Z_Z_QUAD`，说明候选上限会改变部分计划选择。该结果只说明 plan-only 阶段的候选/验证预算可以小幅缩短，不能说明计划质量或执行效率改善。

### 3.2 单查询 TS 计划选择诊断

在独立 plan-only 检查中，同一查询上经典 CBO 选 `P_T`、计划约 500 ms；启用高级索引的 KART 选 `P_TS`、计划约 743 ms。两者均未调用 LLM。该条记录说明 TS 可以被选择，同时显示这一条查询上 KART 规划更慢；它没有执行时间，也不能用来判断 `P_TS` 的执行优势。

### 3.3 `P_TS` 强制执行微基准

- 查询：`advdiag_st_long_wide`。
- 运行方式：固定计划 `P_TS`，TS 范围预算分别取默认 64 与实验值 8，各 3 次；比较的是执行和索引阶段计时，不包含计划搜索时间。
- 正确性：两种范围预算均返回 1,350 条结果，trajectory ID 顺序与冻结的 FullScan Oracle 完全一致。

| TS 最大范围数 | 实际发出的扫描任务 | 三次 `t_exec` | `t_exec` 中位数 | 索引阶段中位数 |
|---:|---:|---:|---:|---:|
| 64（默认） | 256 | 1496 / 1617 / 1661 ms | 1617 ms | 369 ms |
| 8 | 32 | 1342 / 2008 / 1383 ms | 1383 ms | 251 ms |

cap 8 将发出的扫描任务减少到八分之一，索引阶段中位数下降约 32%。但三次 `t_exec` 均值只从约 1591.3 ms 降至约 1577.7 ms，下降约 0.9%；中位数虽然下降约 14.5%，但 cap 8 的一次 2008 ms 波动很明显，因此当前不能称为稳定执行收益。

默认预算下原始 posting 数为 33,813；cap 8 合并后为 34,290。精确码过滤后均为 33,813，和 Oracle 的最终答案一致。这说明粗范围合并确实减少了扫描任务，同时增加了约 477 条 gap postings 的读取，再由精确过滤剔除。另一次 cap 8、验证候选上限 3 的诊断出现 `t_exec=5503 ms`，其中 `fetch=3267 ms`；该记录进一步显示回表/Fetch 阶段及运行波动仍可能主导总执行时间，不能与上述 6 次测量混作同一配对均值。

### 3.4 较早的 12 查询 E2E pilot（仅作历史参考）

2026-10-14 的一轮 pilot 有 48 条结果记录，Oracle 检查为 48/48 通过，KART/CBO E2E p50 分别约 255/277 ms。该轮当时的 CBO 高级索引开关没有被可靠隔离，缓存也不是真正冷缓存；因此它只能说明该 pilot 的答案与 Oracle 一致以及记录到的延迟分布，不能支撑 KART 公平地胜过 CBO 的结论。不得用这组 p50 覆盖本轮尚未解决的 E2E 目标。

## 4. 本地验证

修复 trace 计数残留调用后，在 WSL 下以离线 Maven 运行 10 个聚焦测试类，共 60 项：`CodeRangeBudgetTest`、`TShapeIndexAdapterLimitTest`、`ExecutionTraceP5Test`、`BeamSearchAcceptanceTest`、`AdvQueryRouterTest`、`AdvFinalCalibratorTest`、`AdvancedRewriteSurvivalTest`、`PlanValidatorTest`、`CostFeaturesExtractorAlignTest` 和 `CostModelTest`。结果为 **60 passed / 0 failed / 0 errors / 0 skipped**。

这些是编译和单元/轻量机制测试，不包含服务器全量 E2E，不证明 CBO 对比胜出，也不替代多轮配对统计。

## 5. 公平性、真实性与证据边界

1. **结果集正确性与计划优劣是两件事。**TS 微基准对一条查询通过冻结 FullScan Oracle，是该查询与该快照上的正确性证据，不是整个工作负载的无漏查证明，也不是速度优胜证明。
2. **12 条查询是诊断样本。**虽然按固定种子和查询族生成且没有使用方法胜负挑样，但样本数量不足以估计总体高级索引采用率、延迟分布或胜率。
3. **执行实验不是 CBO 对照。**强制 `P_TS` 的范围预算比较只测 TS 执行路径，没有在同一查询、同一 trial、同快照下同时测 CBO 计划并计算净 E2E。
4. **plan-only 数据不代表执行质量。**`P_TS` 被选中只证明候选能到达 Final 选择；最终胜负仍取决于实际执行成本和规划成本。
5. **LLM 的贡献没有被检验。**当前关键 plan-only 和 TS 微基准零 LLM 调用，不能将任何局部收益归因于 LLM。
6. **计量限制需保留。**`emitted_ranges` 是实际构造/发出的 ScanTask 数，不是 RegionServer RPC 数；当前没有观测到真实 HBase RPC 的指标时仍应记为不可得，不能拿客户端任务数代替。
7. **本轮没有运行全量 suite。**本轮工作限定为代码复核、轻量单测和已有的小规模服务器诊断，没有启动正式或全量实验。此前全量 suite 入口因服务器副本缺少 `.env` 且会检查 LLM API key 而未启动；没有复制密钥或用假 key 绕过。服务器目录中的历史结果需与其提交、manifest、缓存状态和环境配置一起归档后再纳入严格配对比较。
