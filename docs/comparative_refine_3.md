# 第三轮对比实验优化：覆盖验证算法与 LLM 延迟诊断

日期：2026-10-01。

## 1. 目标与状态

本方案承接 [第二轮指导](comparative_refine_2.md) 和 [第二轮交付物](refine_2/summary.md)。目标是在 CBO-first、当前查询真实调用 LLM、完整安全验证的约束下，减少 hybrid 的额外成本，并重新评估端到端净胜空间。

**本文件是待实施的指导，不是第三轮完成报告。** 编写时仅新增本文，未修改代码、未运行实验。测量数字来自第二轮交付包；代码观察来自本地源码，开发前需核对服务器构建是否一致。

本轮优先顺序：

1. 分解 PlanValidator 内部耗时。
2. 消除反复区间解码和逐覆盖点全表遍历。
3. 单独诊断 LLM 与 safety 并行时的延迟。
4. 两臂使用同一新验证器，重新做小规模配对。
5. 仅在预算可行后继续校准和未知查询验证。

不扩全量、不新增数据集、不人为弱化 CBO；先利用已有开发案例完成机制诊断。

## 2. 证据更新：哪些结论成立，哪些仍待测

### 2.1 已测：主要耗时在 safety

[prepare_breakdown](refine_2/prepare_breakdown.md) 的 full 模式记录：

- AIS DTW：8,064 个扫描任务；safety 26,649 ms，features 7 ms，Region 定位 5 ms，prepare 26,660 ms。
- AIS Fréchet：3,456 个扫描任务；safety 5,856 ms，features 2 ms，prepare 5,860 ms。
- safety_only 模式去掉 features 后，DTW safety 仍为 35,796 ms，Fréchet 为 5,662 ms。

因此，继续优化 Final features/Region 不是当前主线。先前“特征提取可能主导”的假设已被本包测量否定。

### 2.2 已测：LLM 当前无增量且更慢

[独立决策报告](refine_2/llm_independent_decision.md)显示：9/9 最终选择与 FastCost rank_hint 一致，0 次 keep_cbo，0 次分歧；LLM 耗时约 2.9–21.3 秒。取消强制 prefer 后，当前模型和提示仍未证明额外决策价值。

[运行配置](refine_2/RUN_CONFIG.md)为本地 Qwen2.5 1.5B、输出上限 96 tokens、调用预算 120 秒、一次调用、一次 trial。第二轮 E2E 仍为 0 胜。

输出上限不是实际输出长度；一次 trial 不能确定延迟分布。尚不能把变慢全部归因到提示变长或 CPU 争用。

### 2.3 源码可见：覆盖检查反复扫描与解码

本地 `PlanValidator.coverageCheck` 枚举时间桶/空间单元并调用 `coveredBy`。`coveredBy` 为每个覆盖点遍历任务，并调用 `ScanTask.startBytes()`、`stopBytes()`。当前这两个方法每次从十六进制字符串重新解码字节数组。

设覆盖点数为 M、任务数为 N，覆盖查询最坏为 O(M×N)，并包含重复分配、字符串处理和解码。若两者规模接近，表现为近似二次增长。

这是可确认的实现结构，**尚未通过内部 profiling 证明其占全部 safety 的比例**。不要把 26.6 秒直接全部分配给 coveredBy，也不能仅凭两条查询推导精确复杂度曲线。

## 3. 固定公平性与归因要求

- CBO 搜索与选择规则不变；公共验证器优化对 CBO 和 hybrid 一致生效。
- 全部安全检查保留，不以“编译器生成的计划应该安全”为由跳过验证。
- 不新增强非 LLM 正式比较臂；内部计时和归因实验单独标记。
- 不硬编码计划赢家，不按结果删除负收益查询。
- 已有九条是开发集合，不重新命名为 holdout。
- 不用旧 CBO 与新 hybrid 比较来证明相对优势。
- 保留错误、超时、回退、投机浪费、后台残留工作。
- 验证加速属于公共工程收益；LLM 增量需要独立证据。

## 4. 阶段 A：验证器内部观测

### 4.1 开发入口

- `src/main/java/kart/validation/PlanValidator.java`：各检查、coveredBy、证书生成。
- `src/main/java/kart/compile/ScanTask.java`：区间解码和可变字段。
- `src/main/java/kart/validation/CoverageCertificate.java`：证书内容。
- `src/main/java/kart/query/QueryEngine.java`：验证器构造及调用计时。

记录服务器构建哈希、源码版本/dirty 状态、JVM、数据快照和参数。不要直接把本地文件视为服务器二进制证据。

### 4.2 建议字段

以下字段均为建议新增：

- `t_validator_init_ms`：schema 等初始化；确认它是否被原 safety 区间包括。
- `t_structure_ms`、`t_semantic_ms`、`t_coverage_ms`、`t_physical_safety_ms`。
- coverage 内部的区间准备、覆盖点生成、查找、证书构造耗时。
- `coverage_probe_count`、`range_count`、`range_compare_count`、`range_decode_count`。
- GC/分配的抽样 profiling 结果（必要时），不要在每个比较中打印日志。

使用单调时钟。父子阶段不可重复求和，细粒度计数尽量使用低开销累加。若插桩明显影响耗时，用独立 profiling 跑次解释热点，性能比较用固定的低开销观测配置。

### 4.3 最小诊断

先在固定计划上隔离验证器，无需执行 HBase 查询或调用 LLM。保留相同 BoundIR、布局和扫描任务。

按固定种子构造不同数量的合法扫描任务及覆盖点，观察增长趋势；例如从数百到 1k、2k、4k、8k。记录实际 M、N 和覆盖命中位置，不能只用 n_scan 推断复杂度。

若主要成本不是 coveredBy，就按实际热点调整，不强行完成预设重构。

**期望收获：**确定二次遍历、解码、证书字符串或其他检查各占多少，给优化提供直接证据。

## 5. 阶段 B1：一次验证只解码一次

### 实施指导

1. 验证入口为扫描任务建立局部只读视图，包含源节点、表、分片、start/stop 字节及原任务引用。
2. 每个边界解码一次，后续覆盖与物理安全检查共用。
3. 保留空值、非法十六进制、边界反转、截断、错表、错分片等拒绝行为；异常不得变成通过。
4. 不先在可变 `ScanTask` 上增加无失效逻辑的永久缓存。其公开 startHex/stopHex 变化时，旧字节会失效。
5. 如果后续改成不可变对象，再单独评估跨阶段复用。

这是相对容易隔离的第一步：只降低重复解码，不改变覆盖查找语义。

### 验收

- 旧、新路径接受/拒绝结果一致。
- 解码次数由内层比较次数级降至任务数级。
- 单独报告验证耗时、分配/GC变化，不提前承诺数量级收益。

**期望收获：**确认重复字符串解码是否是重要成本，并为区间索引提供稳定输入。

## 6. 阶段 B2：用区间索引替代反复全表扫描

### 6.1 索引边界

按访问节点、表组织区间，必要时按经过验证的分片边界进一步分组。不能让其他节点或其他表的范围补足当前节点缺口。

使用与 RowKey 相同的无符号字节比较，保留 `[start, stop)` 语义。先确认输入边界有效，再构造索引；对错误输入仍失败关闭。

### 6.2 可选实现

初版优先选择容易证明等价的方式：

- 区间按 start 排序，构造前缀最大 stop；对 probe 查找最后一个 start≤probe 的位置，再判断此前最大 stop>probe。
- 或将有效重叠/相邻区间合并为用于查找的并集，随后二分。

不能只检查“start 最大的一个原始区间”的 stop：嵌套区间场景下，更早的长区间可能覆盖 probe，而较晚的短区间不覆盖。

索引仅用于验证，不必修改实际执行任务。若 M 个 probe 独立二分，总成本可降为 O(N log N + M log N)；若 probe 可保持正确排序，可进一步使用有序扫描。空间成本和证书构造仍需单独衡量。

### 6.3 安全语义边界

本轮优先保持原检查行为。旧检查通过不等于数学上完整证明了所有可能覆盖情形，不能把旧实现作为唯一安全真值。

如发现旧验证只检查代表点而遗漏完整区间义务，应单独记录具体反例和修复，不能悄悄混入性能优化。性能等价测试之外，还应按预期覆盖不变量进行边界和负例测试。

不能仅信任 `coverageRef`、计划 ID 或已有证书文本。证书摘要化若确有必要，须保留可核查的覆盖义务和诊断能力，并作为独立改动。

### 6.4 必测案例

- 相邻区间边界、单点落在 stop 上、范围内部孔洞。
- 重叠、嵌套、重复、乱序区间。
- 缺失一个时间桶/空间单元/分片。
- 错表、错节点归属、错分片、跨分片非法范围。
- 空/非法边界、start≥stop、truncated=true。
- 固定种子随机区间与 probe：旧、新点覆盖结果一致，并与简单参考实现比对。
- 原有合法计划、安全拒绝测试和小规模 Oracle 回归。

**期望收获：**降低首次 novel 计划验证的成本。缓存只能帮助已见计划，本阶段直接作用于第一次验证。

## 7. 阶段 C：LLM 延迟的隔离实验

### 7.1 先分清原因

保持模型和请求内容完全相同，比较：

1. LLM 单独执行，验证器不运行。
2. LLM 与旧验证器并行。
3. LLM 与新验证器并行。

这些是开发诊断配置，不是新增正式比较方法。固定运行顺序轮换与重复次数，预先约定预热方式；不只选最短一次。

记录模型加载、实际输入/输出 tokens、提示处理、生成、服务端总时间、客户端墙钟、CPU/GPU、内存、GC与并行任务起止。

若当前兼容接口无法提供某些服务指标，标为不可用；必要时用服务日志或单独诊断接口，但注明路径差异。不能把客户端总耗时减去未知阶段后命名为精确排队时间。

### 7.2 判断与动作

- 单独快、并行慢：优先调查共享 CPU、线程调度、内存和 GC；先验证新验证器是否减轻争用。
- 单独也慢且提示处理主导：压缩输入，保留必要区分特征。
- 生成主导：只输出 action/plan_id，减少无用文本；输出上限依据实际格式设置，避免截断 JSON。
- 加载主导：模型常驻并明确冷/热协议。
- 服务排队主导：控制并发，禁止把积压排除在 E2E 之外。

这些是条件分支，不是当前已经确认的原因。

### 7.3 预算

120 秒调用预算只适合当前诊断取证，不能视为默认最优策略。新预算应结合优化后的 CBO 残余时间和候选收益确定。

短超时可限制损失，但无法产生收益；超时后仍在运行的推理要记录取消和资源成本。不得把超时行从分母删除。

**期望收获：**确认 3–21 秒延迟是否来自推理本身、输出、排队或验证器竞争，并判断能否回到足以覆盖的成本范围。

## 8. 阶段 D：rank_hint 与信息价值诊断

当前 9/9 跟随 hint 尚未证明 LLM 的额外价值。建议内部对比：

- 保留 hint 的现有提示。
- 去掉 hint，但保留同样候选特征。
- 去掉 hint 并轮换展示顺序，用来检查位置偏好。

先固定模型和输出协议，再改变信息；不要同时换模型、候选与提示。仅产生不同选择不算成功，必须比较其合法性、执行收益和实际新增延迟。

输入至少应提供可用于判断的扫描范围、预计回表量、联合选择率和估计不确定性。若只有计划 ID 和查询概述，去掉 hint 不会自动创造决策依据。

所有特征必须在当前执行前可得；测试实测赢家、当前执行扫描量或答案不得回流到在线输入。特征收集本身有成本时计入规划。

如果仍无增量，转向分组留出的相对收益校准；不通过强迫模型改变答案、拉长提示或事后选择查询制造价值。校准器收益与 LLM 收益分别归因。

**期望收获：**区分 hint 锚定、信息不足和当前模型决策能力的限制，而不是仅凭九条一致选择得出普遍结论。

## 9. 阶段 E：统一新验证器后的公平配对

### 9.1 重新计算预算

两臂统一升级后重新记录：

```text
T_cbo_new：新 CBO 的真实 E2E
C_new：hybrid 的 CBO-first 阶段
L_new：LLM 调用
V_new：额外候选准备
E_new：候选执行
R_new：其他关键路径开销
```

当候选提前投机、最终被采用，且 LLM 与候选工作可重叠时，近似条件为：

```text
C_new + max(L_new, V_new + E_new) + R_new < T_cbo_new
```

该公式只用于预算解释。不同候选、串行准备、取消与调度必须用实际事件时间线计算，真实 E2E 以请求开始到答案可返回为准。

上一轮约 0.9 秒/1.9 秒预算不再直接适用：公共优化可能同时大幅降低 CBO 规划。不能把 CBO 原来的慢验证时间永久当成可隐藏 LLM 的窗口。

### 9.2 小规模推进

先使用 AIS Fréchet 和 DTW，保留 AIS 小查询与已有 T-Drive 作为退化对照。已有集合全部保持开发身份。

建议固定预热后做 3 次开发配对作为初步检查；如果波动导致结论不清，标为不确定，再按事前约定增加测量，而非跑到获胜为止。三次也不是正式统计证明。

固定缓存协议、总资源预算和 Oracle；轮换两臂顺序，确保上一任务真正结束。旧结果仅作历史背景，新结论基于同配置的新 CBO 与新 hybrid。

### 9.3 输出

按 query/trial 记录：计划、候选与 hint、最终来源、Oracle、各阶段耗时、真实 E2E、净收益、超时/回退、资源状态和投机浪费。

报告均值/中位差值、胜平负、最差退化、总耗时和完成率。小样本不以 P99 为主结论，不把失败行排除后宣布改善。

**期望收获：**确认工程优化是否转化成相对优势，以及 LLM 是否仍构成不可覆盖的延迟下界。

## 10. 阶段门槛与停止条件

### 可以继续

- 验证器热点已定位，算法优化通过安全与等价性测试。
- 解码/比较次数按预期减少，真实验证墙钟降低。
- LLM 隔离实验能够解释主要延迟来源。
- 新基线下至少存在可复现的正净收益空间，才扩大机制验证。

### 暂停或转向

- 验证器已快，但 `L_new` 仍超过可用残余时间：先降推理成本，不扩全量。
- 单独更快的候选无法在投机中复现：检查竞争、缓存和调度。
- 选择正确但净收益不成立：报告计划质量与 E2E 的区别。
- LLM 始终无增量：完成校准或重新定义其任务，不宣称 LLM 有效。
- 新 CBO 同步变快，收益窗口消失：如实接受该边界，不保留慢验证器给 CBO。

收益门控只减少坏执行，无法收回已支付的 LLM 时间。在逐条调用并等待的要求下，部分短查询可能始终不具备净胜空间。

## 12. 本轮最终应获得的答案

1. safety 中多少成本来自重复扫描、解码和证书构造？
2. 保持安全语义后，首次验证可降低到什么水平？
3. LLM 慢是否与验证器并行争用有关？
4. 公共验证器优化后，新的 CBO 还留有多少收益窗口？
5. 不依赖 rank_hint，LLM 能否作出更有价值的选择？
6. 净收益是否真实、可复现，代价与有效场景是什么？

推荐本轮核心交付收敛为：**验证器算法优化 + LLM 隔离诊断 + 新基线配对**。只有这些证据支持继续，才推进更多查询与全量实验；不预设第三轮必然超过 CBO。
