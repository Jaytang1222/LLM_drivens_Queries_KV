# KART + CBO + 本地 LLM 对比实验优化指导

更新日期：2026-10-01。

## 1. 目标、证据与使用边界

本方案的目标是在 **CBO-first、LLM-on** 的前提下，提高 hybrid 相对原生 CBO 的端到端净收益。保持原生 CBO 实现、正确性要求和比较方法不变，重点处理 E2（BoundIR→计划）和 E3（BoundIR→答案），不涉及 NL→IR。

本文件是待实施的开发与诊断方案，**不是优化已经完成或实验已经通过的报告**。本次仅编写文档，未运行服务器实验。下述最新结果来自用户提供的实验总结，未在本次重新读取服务器原始结果：

- T-Drive 4q 和 AIS census 尚未观察到 hybrid 的 E2E 胜出；AIS 的查询总数与逐行耗时本次未提供，不补造统计。
- 已能提出并投机执行 novel 计划，但串行新增规划成本常超过执行节省。
- AIS 的 `validateFixed` 较重，`await` 可达数十秒；具体耗时归属仍需拆分确认。
- v6 去掉固定 `P_T` 偏好后，FastCost 常排出 `P_Z`，同轮执行节省 `S≤0`。
- `prefer=P_T` 探针说明某些查询可能存在更快计划，不能直接作为全量主策略。

以上支持“规划开销与候选排序值得优先诊断”，尚不能证明数据集没有机会、FastCost 存在代码错误，或 LLM 必然能够纠正排序。

### 必须坚持的边界

1. 不弱化 CBO，不给 CBO 增加人为错误，不跳过 hybrid 的安全验证。
2. 不按 KART 胜负替换测试查询，不把查询 ID→赢家映射写入主策略。
3. 保留失败、超时、回退与负收益；不只统计成功采用新计划的子集。
4. 不新增强非 LLM 正式对照臂；可在开发集做内部归因诊断，并明确其用途。
5. 计划安全、计划新颖、执行更快、端到端更快是四个不同指标。
6. 优化可以提高获胜机会，不能预先保证全量工作负载胜过 CBO。

## 2. 先固定 LLM-on 与计时契约

### 2.1 推荐主口径：LLM 在当前查询决策路径上

每条正常进入规划流程的查询调用一次 LLM，记录请求是否真正发出、是否完成、是否被采用。LLM 可建议保留 CBO；超时或非法输出回退 CBO。回退行仍进入总体统计。

不能仅凭 `llm_calls=1` 就认定 LLM 有贡献。至少区分 requested、completed、valid_proposal、adopted、fallback 五种状态。若允许超时后返回，记录请求取消是否成功以及残留计算成本。

另一种可选服务模式是 CBO 先返回、LLM 后台学习。它可能保护短查询，但该次答案没有使用尚未完成的 LLM 决策，必须单独报告，不能用于证明当前查询上的 LLM 决策获胜。本轮优先优化前一种口径。

### 2.2 串行与投机计时不能混用

串行场景定义：

```text
T_cbo = P_cbo + E_cbo
T_hybrid = P_hybrid + E_selected
S = E_cbo - E_selected
H = P_hybrid - P_cbo
净收益 G = T_cbo - T_hybrid = S - H
```

`G>0` 才是该配对下的 E2E 净胜；实际验收还要排除计时噪声。

投机场景中，执行与规划有重叠，不能把两个完整区间直接相加当 E2E。必须用单调时钟记录请求开始到答案可返回的真实墙钟时间。分别记录规划结束、候选执行开始/结束、选择确定、答案就绪及清理结束。

若候选已经可以提前执行，但必须等 LLM 完成才能采用，理想下界受 `max(LLM完成时间, 候选完成时间)` 限制；验证前置、调度、资源争用和清理可能进一步增加延迟。若候选必须等 LLM 提出后才开始执行，则不能套用这个完全重叠的理想假设。

为兼容旧字段，可另报 `t_exec_after_plan`，使 `t_e2e = t_plan_wall + t_exec_after_plan`，但这个字段不是完整执行耗时。完整执行时间另记 `t_exec_wall`，并保存原始事件时间线。

## 3. 阶段一：测量现有计划空间的可获益上界

### 操作步骤

1. 冻结已有开发查询、BoundIR、快照、索引布局、Oracle、CBO 配置与候选构造规则。
2. 对每条开发查询枚举当前可构造候选，记录哪些在 CBO 原候选集合内、哪些在集合外。枚举不完整时标为“已测候选池”，不能声称是全计划空间。
3. 对合法候选分别测执行时间，并对执行结果做 Oracle 比较。非法候选不参与最快合法计划排名。
4. 在可控缓存协议下轮换候选执行顺序；配对记录 query/trial，不用不同机器状态下的独立最小值拼出收益。
5. 用开发重复测量估计每个候选的典型耗时与波动。候选很多时，从单次观测选最小值会产生乐观偏差，应另轮确认。
6. 计算已测合法候选中最快者相对 CBO 的执行节省，结合实测 LLM、验证开销估算串行与投机是否存在净收益空间。

建议每条查询输出：CBO 计划、最快已测合法计划、候选池大小、执行节省、额外规划开销、理想净收益、实际 hybrid 净收益和误差范围。

### 如何解释

- 最快候选也只节省很少：优先降低固定开销；继续调排序无法创造不存在的执行收益。
- 存在稳定且足够大的节省，但 hybrid 没选到：优先修正排序和选择信息。
- 选中了较快计划，仍不净胜：优先压缩验证/LLM关键路径。
- 单独执行更快，投机时变慢：检查共享 HBase 资源争用、取消与残留任务。

**期望收获：**确定瓶颈是机会不足、选错计划、规划太慢还是并发干扰，得到后续优化投入的依据。事后最快计划仅作为诊断上界，不是可部署方法成绩，也不得向在线提示泄露测试赢家。

## 4. 阶段二：拆解 AIS 验证与等待耗时

优先检查 `CboLlmProposalArm`、`QueryEngine.validateFixed`、`runFixed` 及 Future 等待/清理路径。方法名不能证明其中只进行了安全验证。

### 建议事件与耗时字段

- CBO 搜索与候选构造。
- 元数据读取：来源、请求次数、缓存命中、读取耗时。
- 逻辑安全检查、覆盖检查、版本检查、物理编译。
- 投机任务排队、验证、实际执行。
- LLM 排队、模型加载、提示处理、生成、响应解析。
- 主线程等待开始/结束、等待的具体 Future、任务阶段。
- 取消请求、取消确认、资源释放、后台任务彻底结束。

所有事件带 query/trial/arm/candidate/task ID。异步子任务和主线程使用可关联的同一进程单调时间轴。`await` 与被等待任务的耗时通常重叠，不能重复累计。

### 允许的优化

1. 同一查询、同一快照内复用已获取的不可变元数据和构造结果。
2. 相同计划的验证结果只在语义、快照、索引布局与规则版本均一致时复用。
3. 检查是否重复编译/重复验证；确认后消除重复工作。
4. 超时取消必须覆盖实际底层工作。Future 标记取消不代表 HBase RPC 已停止；无法及时停止时隔离并报告残留任务，不让它污染下一条基准查询。

这些是待检查项，不表示当前实现已经存在全部问题。不得为了降延迟删除合法性、覆盖或精确过滤检查。

**期望收获：**把“等待几十秒”归因到具体阶段，识别能够安全消除的开销；若大部分等待实际来自执行，应转向执行和竞争诊断。

## 5. 阶段三：预测相对 CBO 的真实收益

### 5.1 标签与输入

对开发查询的候选建立标签：`S(q,p)=E_cbo(q)-E_p(q)`。同时保留重复测量波动，避免只拟合一个偶然赢家。

在线可用特征建议包括：

- 时间/空间选择率及联合选择率、相关性统计。
- 索引扫描范围数、预计扫描行数、chunk 数量。
- 回表数量、随机读取比例、数据局部性。
- 交并集、去重、精确过滤和合并的预计工作量。
- 索引布局、快照规模、已有成本估计及历史估计残差。

每个特征标明“统计估计”或“历史实测”。当前测试查询执行后得到的实际扫描行数与耗时只能作为分析标签，不能伪装成执行前可用特征。若需在线探针，其耗时和资源必须计入 hybrid。

### 5.2 训练与选择

1. 先用简单回归或树模型校准收益，不急于微调大模型。
2. 按模板、时间区间、空间区域分组隔离开发与验证数据，去除语义近重复。
3. 在开发数据上校准不确定性和阈值；未验证校准前，不把模型分数称为可信概率或置信下界。
4. 在线比较候选相对 CBO 的预期收益，而非仅比较 FastCost 的绝对分数。
5. 收益不足或不确定时保留 CBO。已经支付的 LLM 开销仍计入总耗时，回退不等于无成本。

**期望收获：**减少 `P_Z` 等候选被错误高排的情况，降低执行 regret；是否能净胜仍由 E3 墙钟时间判断。

## 6. 给 LLM 明确且可归因的任务

LLM 输入应包含精简 BoundIR、CBO 方案、少量合法候选摘要、可用联合统计与校准成本。避免只输入同一组错误分数，再期待 LLM 无依据地纠正它们。

一次调用输出一个结构化决策：保留 CBO，或提议一个可构造候选；可附受限的原因码，例如空间时间相关性、回表成本或范围碎片化。原因码便于分析，不当作正确性证明。

若仍要求只提议 CBO 候选集合外的计划，应明确：这种任务只能修复候选遗漏，无法修复 CBO 已有候选之间的排序错误。若普查主要暴露排序错误，可把“重排已有候选”作为单独版本研究，标记任务变化，不混用新计划发现率。

推荐流程：

```text
CBO SafePlan → 构造/提取少量候选摘要 → 一次 LLM 决策
→ 确定性合法性与安全验证 → 保守收益判断 → 采用或回退
```

禁止第二轮无界搜索补救非法输出。无候选、非法输出、超时、验证失败和收益不足分别记录原因。无候选时如果主协议要求逐条 LLM-on，可调用紧凑的保留 CBO 决策；零调用快路径必须作为另一协议报告。

内部归因可比较“校准排序本身”和“校准排序加 LLM 决策”，无需新增正式对照臂。若收益主要来自校准器，应如实归因；若 LLM 总是照搬其第一名，尚不能证明 LLM 带来额外价值。

**期望收获：**回答 LLM 是否改善决策、在哪类查询有效，以及其决策收益是否覆盖调用成本。

## 7. 阶段四：有界投机与模型降延迟

### 7.1 先限制投机规模

初期最多投机一个候选，开发阶段采用如下门槛思想：

```text
保守预测的执行节省 > 额外关键路径开销 + 并发争用余量
```

该门槛是决策近似，不替代真实 E2E 验证。若候选选择发生在 LLM 返回前，应明确由哪个排序器决定；LLM 最后拒绝该候选时，其全部投机成本仍保留。

先确认实际调度是“候选执行与 LLM 重叠”，还是还同时运行 CBO 执行。两者资源需求不同。固定总线程、连接和 RPC 预算；额外资源若不可避免，必须报告资源成本，并避免把额外资源收益全部归因于计划质量。

### 7.2 Ollama 优化顺序

1. 分离模型冷加载与稳态请求；模型常驻效果单独确认。
2. 精简输入，仅保留决策必要特征，不传全量候选树和冗长日志。
3. 使用短结构化输出和合理输出长度限制；约束解码能力以当前模型/服务实际支持为准。
4. 模型支持时关闭不必要的长思考；不要假设所有模型都有同一开关。
5. 用更小模型做开发对比，同时评估合法率、选择 regret、E2E 净收益和 P95；参数更少不保证具体硬件上更快。
6. 检查推理与 HBase 是否争用 CPU/内存；调整并发和部署资源时记录配置。

调用预算应由实测可节省时间决定，不把历史 1500 ms 当作普适最佳值。对短查询而言，即使 1500 ms 也可能超过 CBO 整段执行。

### 7.3 缓存单独评估

主比较先关闭计划决策缓存；缓存命中收益另报。仅缓存计划/验证所需的可复用信息，不缓存答案。键至少含规范化 BoundIR、快照、索引布局和计划规则版本；模型决策缓存还应绑定模型、提示和校准器版本。

命中后检查版本并重新进行必要验证。若命中直接跳过 LLM，该行不能归入逐条 LLM-on 主结果。模型常驻、服务端提示前缀缓存和计划缓存是不同机制，分别记录。

**期望收获：**在不明显损害选择质量的情况下，降低调用与关键路径耗时，并明确吞吐/资源代价。

## 9. 逐行记录与比较方法

每行至少记录：

- 身份：query、trial、arm、workload/snapshot/config/build 哈希、执行顺序。
- 决策：CBO 计划、CBO 候选集、提议计划、最终计划、novel、合法性、回退原因。
- LLM：requested/completed/adopted、调用数、模型、输入输出 token、超时、加载/排队/生成时间。无法获取的字段保留缺失原因，不填假零。
- 时间：CBO 规划、hybrid 规划、验证、完整执行、真实 E2E、等待和清理。
- 投机：候选数量、开始/结束、是否采用、浪费工作、取消成功与残留任务。
- 结果：Oracle、错误/超时、缓存协议及实际执行状态。

按同一 query/trial 计算 `G=T_cbo-T_hybrid`，先在查询内部汇总，再汇总工作负载，避免重复次数多的查询得到额外权重。报告平均/中位净收益、胜平负、总体耗时、E2E P50/P95、最差退化、失败数。小样本 P99 很不稳定，不作为主要结论。

胜负应结合开发阶段确定的噪声容忍范围；幅度落在范围内标为平局。重试与超时采用事先固定规则，不能删除失败后只对成功行计算平均值。必要时同时给完成率与约定超时惩罚下的汇总。

E2 主要检验规划质量与成本；实际答案正确性和执行收益需 E3 或明确的逐计划执行证据。E2 的 `plan_ok` 不等于实测选优准确率。

## 10. 测试、验收与推进顺序

### 10.1 先做轻量逻辑测试

- 无 novel 候选、重复提议、非法计划、验证失败、超时均正确回退。
- 收益门槛能拒绝负收益候选；不依赖查询 ID 或固定计划偏好。
- LLM-on 请求与统计一致；缓存短路不会伪装成真实调用。
- 快照/索引/规则/模型版本变化使相应缓存失效。
- 串行计时满足加法关系；投机计时来自真实时间线，不重复累计重叠区间。
- 取消与清理可观测，未结束任务不会悄悄干扰下一轮。
- 安全验证与 Oracle 回归保持通过；错误提议被拒绝属于保护机制，不要求合法 CBO 人为答错。

### 10.2 再做开发诊断

先在已有 T-Drive 与 AIS 开发查询上完成上界与耗时拆解，再做校准、LLM任务与模型优化。已反复查看的查询只用于开发，不再声称是未知测试。

为避免混淆原因，依次改变：计时/重复工作修复、收益排序、LLM输入输出、模型、投机门槛。每一步保留上一版结果和完整配置。

### 10.3 最后冻结新的小规模验证

开发完成后再固定新的验证查询，按事前确定的场景机制与种子抽样，包含正常对照，不能按 hybrid 实测胜负补选。若验证结果用于再次调参，该集合转为开发集。

只有合法计划带来的执行节省稳定覆盖实际新增开销，才能认定该查询上的机制有效。只有冻结集合上的整体指标支持改善，才扩大运行。少数机会查询胜出不能推出全量平均获胜。

### 停止或转向条件

- 已测最快合法候选也覆盖不了开销：当前计划空间下暂停继续调提示，优先压缩开销或研究有依据的执行/计划空间扩展。
- 候选确实有收益但预测持续失败：补充可用统计和代表性开发标签，检查泛化，而非硬编码赢家。
- 校准器提升明显、LLM无额外提升：如实记录归因，重新定义 LLM 的可验证任务。
- 验证质量提高但 E2E 不升：分别报告两者，不把计划质量改善包装成端到端胜出。

## 11. 最终应回答的六个问题

1. 当前候选池中，多少查询存在足以覆盖 LLM 成本的机会？
2. 机会主要来自 CBO 候选遗漏还是成本排序失准？
3. AIS 的长等待究竟花在验证、执行还是调度/清理？
4. 校准后的排序是否在未知查询上减少 regret？
5. LLM 是否在已有排序之上产生额外决策价值？
6. 在一致资源与缓存口径下，收益是否转化为真实 E2E 改善，代价是什么？

推荐立即开展的前三项工作是：**已测候选机会的上界分析 → 验证与等待分段计时 → 相对收益预测**。完成后再决定模型压缩和投机策略的具体参数，不预设实验必胜。
