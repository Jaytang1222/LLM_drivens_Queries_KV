# 第四轮对比实验优化：执行收益校准与低延迟 LLM 决策

日期：2026-10-01。

## 1. 目标、状态与范围

本文件承接 [第三轮方案](comparative_refine_3.md) 和 [第三轮结果](refine_3/summary.md)。目标仍是：在 CBO-first、当前查询真实调用 LLM、完整安全验证条件下，使 hybrid 获得相对原生 CBO 的端到端净收益。

**本文件是待实施指导。** 本次仅新增文档，没有修改代码或运行实验。引用数字来自第三轮已有交付物；第四轮结果尚未产生。

第三轮已解决验证器的主要算法瓶颈。本轮聚焦三件事：

1. 区分计划选择较差、执行路径开销和推理并行竞争。
2. 实施候选相对收益校准，减少错误采纳。
3. 将 LLM 压缩为短决策，降低当前端到端延迟下界。

先使用现有九条开发查询，不立即新增数据集或扩大正式实验。未知查询验证在实现和参数冻结之后进行。

## 2. 已有结果的准确解释

### 2.1 执行不是全面退步

根据 [plan/exec 对照](refine_3/timing_plan_exec.md)，第三轮同包配对中 hybrid 执行阶段为 **4 条更快、5 条更慢**，但 E2E 为 **0 胜、9 负**。

执行更快的四条为：

- AIS DTW：CBO 2,673 ms，hybrid 2,048 ms，节省 625 ms，约 23%。
- AIS Fréchet：CBO 3,907 ms，hybrid 2,780 ms，节省 1,127 ms，约 29%。
- `topk_st_3`：109→73 ms，节省 36 ms。
- `ais_st_control_tiny`：71→30 ms，节省 41 ms。

AIS 两条主要机会仍有执行优势，但 LLM 分别为 4,070/6,828 ms，超过当前可覆盖窗口。

相较第二轮，部分执行时间增加；由于属于不同跑次且当前每条仅一个 trial，不能认定验证器优化造成执行退化，也不能声称这些执行优势已经稳定复现。

### 2.2 慢计划暴露出成本权衡问题

第三轮 [T-Drive 原始行](refine_3/td_e2e.jsonl) 和 [AIS 原始行](refine_3/ais_e2e.jsonl)显示：

- `a2_topk_dtw_wide`：hybrid `P_Z` 回表 chunk 1,647，CBO `P_TZ` 为 66；执行 355 vs 202 ms。
- `ais_st_port_focus`：hybrid 回表 525，CBO 12；执行 580 vs 358 ms。
- `a2_tz_hard_a`：hybrid 索引行数更少，但回表 9,316 vs 5,003；执行 2,669 vs 1,504 ms。
- `ais_st_control_small`：hybrid 回表仅 2，CBO 为 130，但范围数 295 vs 26；执行反而 184 vs 19 ms。

这些是相关证据，不是分段因果测量。它们支持优先评估范围/RPC、扫描、交集和回表之间的权衡，不能单凭回表数或范围数选赢家。

第三轮的公共验证器优化两臂共用，属于真实工程进展；不能将它全部归因于 LLM。

## 3. 本轮固定约束

- 不修改原生 CBO 的选择策略以降低其表现。
- 公共执行器和验证器优化两臂一致使用，并重测基线。
- 不新增强非 LLM 正式比较臂；固定计划、无推理、排序器等配置仅用于开发归因。
- 保持 Oracle、安全验证、错误与超时统计口径一致。
- 不固定偏好 `P_T`/`P_Z`，不使用查询 ID→赢家映射。
- 不按 hybrid 胜负删选查询，不只统计采纳成功的行。
- 主比较关闭跨查询计划决策缓存；复用与模型常驻分别记录。
- 逐条 LLM-on 意味着保留 CBO 也可能支付调用成本。跳过 LLM 的策略如另行研究，必须单独命名，不能混入本轮主结果。
- 不承诺获胜。先证明执行收益和可覆盖预算，再讨论全量效果。

## 4. 阶段 A：同计划独立/并行执行诊断

### 4.1 要回答的问题

第三轮已检查验证器对推理的影响，本轮检查反方向：**LLM 是否拖慢查询执行？** 同时区分候选本身较差和 hybrid 包装路径带来的开销。

### 4.2 固定输入与执行路径

对同一查询选择 CBO 计划和当前 hybrid 提议计划，固定实际物理计划内容及安全验证结果。不能只以 plan ID 相同认定任务、布局和语义相同。

分别运行以下开发配置：

1. 固定计划独立执行，不调用 LLM。
2. 相同固定计划与相同 LLM 请求并行执行。
3. 必要时经 hybrid 执行包装路径执行同一计划，检查调度或重复工作。

验证准备在诊断中单独计时；这种隔离不改变正式 E2E 必须包含准备的要求。

每条采用固定预热和轮换顺序。建议先固定 3 次配对作工程诊断；若波动大，按事前规则扩测或标记不确定，不跑到第一次胜出即停止。记录并行区间实际重叠程度，避免一边已结束却称为并行实验。

### 4.3 建议事件和统计

- 索引扫描起止、实际行数、范围数、RPC 数。
- 候选合并/交集/去重耗时及输出规模。
- chunk 回表和完整轨迹读取分别计时，避免混为同一 fetch。
- 精确过滤、相似度计算、Top-K 阶段耗时。
- 执行线程排队、CPU、GC、内存及推理重叠区间。
- 执行状态、Oracle、错误、取消和后台任务完成时间。

先核对现有 `fetch_chunks`、`n_ranges`、`dtw_cells` 字段的生产位置与含义，再增加字段；不要仅按名字推断统计单位。父子阶段与并行阶段不可重复求和。

### 4.4 结果分支

- 独立也慢：优先候选排序与执行代价模型。
- 独立快、并行慢：优先推理/执行资源竞争。
- 同计划不同包装路径慢：定位额外排队、重复读取或准备；只有证据出现后才称为实现问题。
- 所有配置波动大：先控制缓存/负载并保留不确定性。

资源隔离若使用更多 CPU/GPU、连接或线程，应明确报告总资源。不能把增加资源的收益全算成计划质量提升。

**期望收获：**解释 execute 差异的来源，决定下一步应改选择器、调度还是公共执行器。

## 5. 阶段 B：实施相对收益校准

### 5.1 预测目标

优先建立两个量：候选执行时间估计，以及相对 CBO 的执行节省：

```text
S(q,p) = E_cbo(q) - E_p(q)
```

独立执行和并行执行的标签分开保存。若并行竞争显著，不能直接用独立标签预测投机表现；可单独估计竞争惩罚，或在固定资源协议下重新校准。

### 5.2 输入特征

优先覆盖已有差异：

- 扫描范围数、碎片程度、预计 RPC。
- 预计索引行数。
- 交集后的候选 chunk 数、去重比例和预计回表量。
- 时间、空间及联合选择率，相关性和统计置信信息。
- 回表局部性、估计读取字节量。
- 合并/交集工作量。
- 相似度类型、参考轨迹长度、预计参与比较数量等公共计算特征。

重点建模 `P_TZ` 的交集削减回表价值与 `P_T/P_Z` 的范围减少收益。不要从本轮个例直接写死系数、阈值或计划偏好。

线上输入必须是执行前可得的估计；实际扫描行数、真实 fetch 和耗时作为离线标签。在线采样若需要额外读取，其时间和资源计入 hybrid。

### 5.3 数据与训练步骤

1. 检查已有普查原始记录是否包含所有已测候选、重复观测和配置，而非只包含赢家摘要。
2. 保留正、负、无收益样本；超时、缺失、未测分别标记。
3. 不把不同快照、资源协议或旧慢验证器的规划时间混为同一执行标签。
4. 对语义重复查询去重，按模板、区域/时间分组隔离训练与验证。
5. 先做简单回归、树模型或成本残差校准，保留可解释特征。
6. 参数与门槛只用开发数据确定。既有九条不能重新命名为未知 holdout。

九条足以检查流程，不足以独立训练并证明泛化。已有普查若也缺少覆盖，应明确缺口，先做管线而不伪造可靠模型。

### 5.4 校准验收

- 在分组验证上报告执行时间误差和相对收益误差。
- 报告候选 top-1 regret、负收益误采纳率和回退率。
- 同时检查错误保守回退是否丢失 AIS 的执行优势。
- 不确定性必须经过检验；任意模型分数不能称为置信下界。
- 校准器推理与特征生成开销计入规划。

**期望收获：**减少五条执行较慢案例的误采纳，同时保留现有正收益。校准器带来的收益如实归因，不自动算为 LLM 增量。

## 6. 阶段 C：压缩 LLM 为短决策

### 6.1 输入输出协议

输入提供紧凑查询摘要、CBO 方案和少量候选特征，包括校准收益与不确定性。不要把单个 rank_hint 写成必须遵守的结论。

输出只保留 KEEP 或候选编号，可使用紧凑结构化格式：

```json
{"choice":"KEEP"}
```

候选编号按请求绑定到合法计划，解析后重新校验。顺序变化时编号映射必须同步；禁止模型直接输出任意执行代码。

先去掉非必要 reason 文本。解释可以离线分析，但离线解释不作为在线决策时已有的证据。服务支持时使用受限输出；实际支持能力需验证，不假定兼容接口一定支持全部约束。

保持一次调用；非法、超时、安全失败按固定规则回退。输出长度上限根据实际 token 和格式测量确定，不能因设得过小造成大量截断再悄悄重试。

### 6.2 模型与部署顺序

1. 保持现有模型，先缩短输出与输入。
2. 记录实际输入/输出 token、加载、提示处理、生成与客户端墙钟。
3. 确認推理硬件和执行器资源重叠，先处理已证实的争用。
4. 再比较更快模型或部署配置，联合考察合法率、regret 和 E2E。

现有 1.5B 已是小模型；参数更少不保证当前硬件上更快。新硬件带来的加速应单列成本，不能隐去资源变化。

### 6.3 开发目标

可先以稳态 LLM 约 1 秒以内作为 AIS 开发目标。这是待验证目标，不是已实现指标或通用预算。实际门槛必须根据新配对的执行收益、重叠方式和额外开销重新确定。

36–41 ms 级执行节省的短查询，即使调用降到 1 秒仍很难净胜。不能通过采纳门控消除已经支付的 LLM 时间。

**期望收获：**把模型等待从当前主要下界降至可能覆盖的范围，并保留可检验的独立选择能力。

## 7. 门控、投机与计时契约

### 7.1 两种架构预算不同

串行决策后执行：

```text
T_hybrid ≈ C + L + V + E + R
```

候选预先投机、最后被 LLM 采用：

```text
T_hybrid ≈ C + max(L, V + E) + R
```

C 是 hybrid CBO-first 阶段，L 是调用，V 是额外准备，E 是候选执行，R 为其他未覆盖关键路径开销。公式用于解释，不替代真实墙钟。

如果 LLM 选择未投机候选、拒绝候选或取消未及时完成，必须按实际时间线记账，不能套用完全重叠的理想式。

### 7.2 两级门控

- 投机前：根据校准收益和不确定性，决定是否启动最多一个候选；仍需遵守逐条调用协议。
- 决策后：结合 LLM 输出、安全检查和收益判断采用或回退。

拒绝投机可以避免浪费，但可能损失重叠机会；LLM 选择不同候选也可能增加等待。所有分支都保留在结果中。

回退 CBO 执行若在 LLM 之后才开始，等待也计入 E2E。若允许 CBO 答案先返回、LLM 后台继续，这是另一种服务协议，不能用于证明本轮“等待 LLM 决策”的获胜。

### 7.3 归因

分别记录投机计划来源、LLM 选择、门控最终选择。只有不同于校准器选择且产生可验证收益，才支持额外决策价值；仅被调用、提出 novel 或与第一名一致都不充分。

## 8. 公共执行器优化：仅由分段证据触发

若阶段 A 证明执行内部仍有明显瓶颈，可进一步研究：

- 回表主导：批量读取、去重、局部性与重复加载。
- RPC/范围主导：语义安全的范围合并和调度。合并可能增加扫描量，不能只减少范围数而不测总成本。
- 相似度主导：先检查已有实现，再考虑精确下界剪枝或 early abandoning。DTW/Fréchet 的适用条件、Top-K 阈值及同分规则需分别验证，不能用近似结果冒充精确答案。

所有公共改进两臂一致生效并重新测 CBO。它们可以提升系统性能，但不保证扩大 hybrid 的相对优势。

**期望收获：**减少真实执行成本，明确收益来自公共执行优化还是计划决策。

## 9. 开发与测试要求

### 9.1 建议检查入口

- `src/main/java/kart/bench/CboLlmProposalArm.java`：投机、调用、选择、门控和回退。
- `src/main/java/kart/query/QueryEngine.java`：准备与执行路径、时间边界。
- `src/main/java/kart/cost/FastCost.java`、`CostFeaturesExtractor.java`：在线特征及校准接入。
- `src/main/java/kart/bench/SuiteRunner.java`：逐行字段与汇总。

具体执行器和推理客户端入口应以当前源码调用链为准。开发前核对服务器构建，不从本地文件推断远端已经更新。

### 9.2 必要测试

- KEEP、合法编号、非法编号、截断、超时和安全拒绝分支。
- 候选展示顺序改变时，编号与计划映射正确。
- 校准只读取在线特征，不读取测试赢家或执行后统计。
- 相同特征/config 得到可复现门控，不依赖 query ID。
- LLM 与投机选择不同、回退和取消路径计时正确。
- 公共执行优化保持 Oracle 和安全不变量。
- 异步区间不重复累加，失败/超时未被过滤。

## 10. 分阶段运行与推进标准

依次冻结以下开发版本，不同时改变所有因素：

1. 第三轮实现加执行分段观测。
2. 同计划独立/并行诊断。
3. 收益校准接入，模型协议暂不变。
4. 短决策协议，候选和资源不变。
5. 如有必要，再变更模型或执行器。

每步记录构建、配置、快照和资源。配对按 query/trial 汇总，轮换顺序；旧历史数字只作背景，不拼接成新的公平对照。

### 推进条件

- 执行差异能被计划或竞争证据解释。
- 校准降低错误采纳，且未系统性损失主要正收益案例。
- LLM 延迟进入实际预算范围，合法率和选择质量可接受。
- 新 CBO 同配置配对下，开发净收益可重复，Oracle 保持通过。

未满足这些条件先不扩全量。单条偶然胜出或仅计划阶段变快不算通过。

## 12. 成功与停止边界

成功分三层：执行选择改善、开发 E2E 净胜、未知查询泛化。三者分别报告，不能互相替代。

若独立 LLM 仍需 4–7 秒、查询总执行只有数秒，当前逐条等待协议可能没有足够窗口。若仅校准器产生收益而 LLM 无增量，应诚实归因。若公共优化使 CBO 同步变快，不能保留慢版本来扩大优势。

开发有效后，先冻结代码/模型/阈值，再生成未按 hybrid 胜负筛选的机制查询；已看结果后继续调参的查询转为开发集。全量优势最终取决于长查询累计收益是否覆盖短查询的调用成本，不能通过事后删查询或改权重保证。

推荐本轮核心路线：**同计划执行诊断 → 相对收益校准 → LLM 短决策 → 新基线配对**。目标是利用已经存在的 AIS 执行收益，并减少其他查询的错误采纳，不预设实验必胜。
