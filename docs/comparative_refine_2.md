# 第二轮对比实验优化：固定候选准备、LLM 决策与端到端净收益

日期：2026-10-01。

## 1. 本轮定位

本文件承接 [第一轮方案](comparative_refine.md) 和 [第一轮交付包](refine/README.md)，将新的开发证据转化为第二轮操作指南。

目标是在 **CBO-first、当前查询真实调用本地ollama LLM** 的条件下，减少 hybrid 的额外开销，提高候选选择质量，验证是否能够获得相对原生 CBO 的端到端净收益。

本文件中的实施步骤均为待开发方案。编写本文件时未修改代码、未运行服务器实验；引用数据来自现有交付包，不代表新测量。九条查询已经用于开发，不能作为未知测试集。

### 固定边界

- 不改变原生 CBO 的搜索、候选选择策略来制造优势。
- 不削弱合法性、覆盖、版本一致性和精确过滤要求。
- 不涉及 NL→IR，不新增强非 LLM 正式比较臂。
- 不硬编码查询 ID→计划，不固定偏好 `P_T`，不按 hybrid 胜负补选查询。
- 不以正确性检查通过或 novel 计划数量代替执行收益。
- 公共执行基础设施的优化应对比较臂一致生效；hybrid 特有的重复工作可以单独消除。
- 不承诺必胜。先验证两条 AIS 开发案例的机制，再验证未知查询上的收益。

## 2. 已有证据及需要修正的解释

### 2.1 开发包尚无 E2E 净胜

根据 [配对结果](refine/paired_e2e_summary.md)：

- T-Drive：4 条开发查询，0 胜、4 负；CBO 总耗时 6,747 ms，hybrid 12,482 ms。
- AIS：5 条开发查询，0 胜、5 负；CBO 总耗时 52,377 ms，hybrid 81,187 ms。
- 这是当前开发配对结果，不是全量胜率或重复实验的置信结论。

根据 [时间拆解](refine/timing_trace.md)：

- `ais_topk_dtw_2week`：CBO 34,567 ms，hybrid 58,113 ms；hybrid CBO 搜索 32,620 ms，LLM 857 ms，候选准备 24,453 ms，候选执行 1,034 ms。
- `ais_topk_frechet_wide`：CBO 14,804 ms，hybrid 17,487 ms；hybrid CBO 搜索 12,360 ms，LLM 1,093 ms，候选准备 4,579 ms，候选执行 543 ms。

这两条 hybrid 已采用 `P_T`。主要损失发生在执行前的额外准备路径，优先调查该路径比立即更换模型更有依据。

### 2.2 “validate 很慢”不等于安全验证本身很慢

本地 `CboLlmProposalArm.validateFixed` 调用 `QueryEngine.runFixed(..., planOnly=true, ...)`。该路径依次包含：

1. 物理计划编译。
2. `PlanValidator` 安全验证。
3. `CostFeaturesExtractor.extractFinal`。
4. 最终成本估计和结果封装。

`extractFinal` 会遍历扫描任务并调用 Region 定位。现有字段 `t_spec_validate_ms` 因而是复合准备耗时，不能直接把 24 秒全部归因到安全检查、网络请求或 DTW 计算。

**待确认：**编译、验证、特征提取、Region 定位分别占多少时间；本地与服务器构建是否一致。当前尚不能断言存在某项具体实现错误。

### 2.3 当前协议限制了 LLM 的独立决策

[LLM 交付报告](refine/llm_decision_eval.md)及本地实现显示：

- 提示要求 prefer 存在于列表时选择 prefer。
- 第一次合法输出不同于 prefer 时，允许向 prefer 纠正的重试。
- 失败时存在 FastCost prefer 辅助选择路径。

因此，“最终选择等于 FastCost 第一名”不充分证明 LLM 没有决策能力。当前协议本身抑制了不同选择。不过，本包展示的 T-Drive 行均为一次调用，不能把这些行的延迟直接归因于第二次重试。

### 2.4 候选收益具有跑次差异

[本轮 T-Drive 上界](refine/td_ub_corrected.md)中，`a2_tz_hard_d` 的更快候选为 `P_Z`，三次执行节省为 451、76、562 ms；旧概括“机会均来自遗漏 P_T”不再适用于全部新结果。

同一查询在 E2E 包中采用 `P_Z` 却未获得执行收益。不能直接认定 `P_Z` 错误，也不能将不同跑次的最快计划当作当前轮真值。第二轮必须保留缓存状态、顺序和配对信息。

机会普查的 FullScan 未测标记也应保留：这是已测候选池中的机会，不是所有物理计划的完整最优性证明。4/4、4/5 来自开发机会集合，不代表总体查询的机会频率。

## 3. 优化顺序与阶段产物

推荐顺序：

1. 固定候选准备拆分计时，定位主要开销。
2. 消除可证明不必要的重复工作，建立轻量安全准备路径。
3. 取消强制 prefer 和向 prefer 纠偏重试，让 LLM 决策可归因。
4. 在分组留出数据上校准相对收益排序。
5. 根据剩余瓶颈优化模型、提示与投机门槛。
6. 冻结实现后再开展新的小规模泛化验证。

每一步保留旧版本配置和结果，避免同时改变候选、模型、缓存、计时后无法解释收益来源。

## 4. 阶段 A：分解固定候选准备成本

### 4.1 开发入口

- `src/main/java/kart/bench/CboLlmProposalArm.java`：候选准备、LLM 请求、投机、等待和回退。
- `src/main/java/kart/query/QueryEngine.java`：`runFixed`、`executeSelected` 和共享执行逻辑。
- `src/main/java/kart/cost/CostFeaturesExtractor.java`：最终特征和 Region 定位。

动手前记录服务器代码/构建哈希、配置、快照和模型版本，确认文件与实际运行产物对应。本地代码观察不能自动代表服务器当前实现。

### 4.2 建议新增观测字段

以下为建议字段，不声称已经实现：

- `t_fixed_compile_ms`：物理计划构造和编译。
- `t_fixed_safety_ms`：完整安全检查。
- `t_fixed_features_ms`：完整特征提取。
- `t_fixed_region_locate_ms`：特征提取内部 Region 定位子阶段。
- `region_locate_calls`、`region_locate_cache_hits`、`n_scan_tasks`。
- `t_fixed_cost_ms`：最终成本卡计算。
- `t_fixed_prepare_ms`：整个候选准备的墙钟时间。
- `t_spec_queue_ms`、`t_spec_exec_ms`、`t_spec_cancel_ms`。

Region 定位属于特征提取的子区间，不要在总和中重复加一次。并行区间也不能简单相加。

每个事件关联 query/trial/arm/candidate/task；使用单调时钟测时，同时保存必要墙钟时间便于查日志。保留现有字段或写明 schema 版本，避免旧汇总脚本误读。

### 4.3 观测后的分支处理

- 编译主导：调查范围展开和重复构造；仅合并语义等价且不会破坏覆盖的工作。
- 安全检查主导：分析重复证明和数据结构开销；不删除检查。
- 特征/Region 定位主导：调查相同请求内重复定位、重复统计读取，确认缓存有效范围。
- 实际执行主导：转向扫描、回表或相似度计算，不能继续把它称为验证瓶颈。
- 等待时间异常而子任务不慢：调查排队、调度、同步和清理。

**期望收获：**明确 24.453 秒和 4.579 秒的组成，找到可实际消除的工作，而非根据函数名猜测。

## 5. 阶段 B：建立可复用的安全准备路径

### 5.1 分离安全可执行状态与成本诊断

建议将概念职责分为：

```text
compileAndValidate → 安全可执行计划
estimateForDecision → 决策所需成本/收益信息
executePrepared → 执行已准备计划
collectDiagnostics → 非决策必需的补充诊断
```

以上是职责示意，不要求按名称机械新增接口。

实施前追踪 `selectedCost`、features、trace 和执行器的所有使用位置：

- 若完整成本卡参与决策或执行调度，不能直接跳过。
- 若只是报告信息，可以离开答案关键路径，但后台计算、清理与资源消耗仍需记录。
- 若改用轻量估计，必须标明估计来源，不将 FastCost 数值伪装成完整最终成本。

### 5.2 允许复用的范围

优先做单请求内复用：相同 BoundIR 的公共统计、只读布局、已编译的同一候选，以及仍有效的验证结果。

跨请求复用至少绑定 BoundIR、快照、索引布局和规则版本；Region 映射还需考虑拓扑变化与底层定位器的刷新机制，不能仅凭快照相同认定位置永不变化。

计划和元数据缓存不得变成答案缓存。主性能比较先关闭跨查询计划决策缓存，避免混淆本轮收益来源。

### 5.3 防止重复执行准备

检查候选从投机线程进入最终执行时，是否重复编译、验证、特征提取或创建等价对象。复用必须绑定同一实际计划和语义，不能因为 plan ID 相同就跨查询复用。

当前不能预先断言存在重复；先通过调用计数和事件轨迹确认，再修改。

### 5.4 公平性处理

保持 CBO 决策算法不变。如果优化发生在两臂共有的编译器、定位器或执行器，新的 CBO 也使用同一实现，并重新测量基线。

如果省去的是 hybrid 已完成 CBO 搜索后再次进行的公共准备，可作为 hybrid 流程优化。记录省去的具体工作，避免把普适基础设施收益归因于 LLM。

**期望收获：**在相同安全保证下，显著缩短额外候选准备。是否足以净胜由真实 E2E 决定。

## 6. 开发耗时预算：如何推导、如何使用

设：

- `C`：hybrid 内 CBO-first 阶段耗时。
- `L`：LLM 调用耗时。
- `V`：额外候选准备耗时。
- `E`：候选执行耗时。
- `R`：其他未包含的关键路径开销。

如果候选在 LLM 完成前已经确定并开始投机，且最后被采用，可近似写为：

```text
T_hybrid ≈ C + max(L, V + E) + R
净胜要求：max(L, V + E) + R < T_cbo - C
```

DTW 当前开发观测：

```text
T_cbo - C = 34567 - 32620 = 1947 ms
E = 1034 ms，L = 857 ms
忽略 R 时，V < 1947 - 1034 = 913 ms
```

Fréchet 当前开发观测：

```text
T_cbo - C = 14804 - 12360 = 2444 ms
E = 543 ms，L = 1093 ms
忽略 R 时，V < 2444 - 543 = 1901 ms
```

这些仅为固定其他耗时的开发预算：

- Fréchet 从约 4.6 秒准备压到明显低于 1.9 秒，较适合作为第一条突破案例。
- DTW 从约 24.5 秒压到明显低于 0.9 秒，需要大幅结构优化。
- 应预留调度和波动余量，达到临界值不等于稳定胜出。
- 公共优化改变 CBO 耗时后必须重新计算预算。
- LLM 选中未投机的候选时不能套用完全重叠公式，需按实际时间线计算。

**期望收获：**明确优化需要多大幅度，而不是只要求“validate 有所下降”。

## 7. 阶段 C：让 LLM 决策独立且可归因

### 7.1 协议修改

1. 去掉“prefer 在列表里就必须选它”的系统指令。
2. 去掉合法选择与 prefer 不同就再次向 prefer 纠正的重试。
3. 初版限制一次调用，输出非法或超时就回退 CBO。
4. 允许明确输出保留 CBO；候选提议仍经相同安全验证。
5. 排序估计可以作为信息提供，但标明不确定性，不作为必须服从的答案。
6. 规则辅助选择必须独立标记，不能算作 LLM 提议成功。为便于归因，本轮初版建议失败直接回退。

结构化输出可采用如下概念协议：

```json
{"action":"keep_cbo","plan_id":null,"reason_code":"insufficient_gain"}
```

或：

```json
{"action":"propose","plan_id":"<allowed_plan_id>","reason_code":"lower_fetch_cost"}
```

原因码限定短枚举，不要求长推理文本。原因码不是收益证据或安全证明。

### 7.2 提供能够区分候选的信息

精简输入包括：查询语义摘要、CBO 计划、少量候选、时间/空间及联合选择率、扫描范围数、回表估计、局部性、估计不确定性。

仅提供当前查询执行前可得到的信息。在线采样有成本时计入规划；当前测试的真实赢家、耗时和答案不能输入模型。

只给计划 ID 和一个错误排名不足以期待模型自行纠正成本。新增特征优先解释已有排序失败，再验证是否改善选择。

### 7.3 与投机的协同

初期仍最多投机一个候选。记录投机选择来自哪个排序器：在 LLM 返回前启动的候选不能归因于尚未产生的 LLM 判断。

LLM 若选择另一候选，应验证并执行真实选择，记录原投机浪费、取消结果和新增等待；不能为复用投机结果而偷偷覆盖模型选择。门控拒绝模型建议时标记“门控回退”。

删除强制 prefer 后，投机命中率可能下降，E2E 可能暂时变差。这是需要测量的设计代价，不能只统计匹配投机的行。

### 7.4 增量价值的判断

开发内部比较同一候选池下的排序器首选与 LLM 选择，不新增正式比较臂：

- 一致：本次未证明额外决策收益。
- 不同且合法：用配对执行测量判断改善还是退化。
- 规则替代或回退：不计为 LLM 自主改善。

**期望收获：**判断此前无增量是否部分由协议造成，并验证开放选择后是否产生足以覆盖调用成本的实际价值。

## 8. 阶段 D：校准候选相对收益

九条开发查询用于验证流程，不足以支撑可靠泛化结论。优先检查已有普查原始数据是否包含完整候选和重复测量，而不是把摘要表当训练集。

### 操作步骤

1. 建立标签 `S(q,p)=E_cbo(q)-E_p(q)`，保留各次观测和波动。
2. 保留负收益、无收益和普通对照；只训练普查赢家会产生选择偏差。
3. 缺失、超时、未测候选分别标记，不能填成零或最慢值而不说明。
4. 加入范围数量、回表规模、联合选择率、相似度类型和统计置信信息。
5. 先用简单回归/树模型或成本残差校准，不急于大模型微调。
6. 按模板、区域、时间区间分组隔离验证；近重复不得跨组。
7. 比较候选排序 regret、收益预测误差、负收益误采纳率，并单独观察端到端收益。

“训练 holdout”不准确：训练只用开发部分，holdout 用来检验泛化。当前反复看过的九条不能通过重新命名变成 holdout。

门控可采用“保守预测收益超过新增关键路径成本”的思想；置信下界必须经校准，不能将任意模型分数直接称为统计置信度。

**期望收获：**降低错误候选被投机或采纳的概率。若收益来自校准器而不是 LLM，应明确归因。

## 9. 阶段 E：降低剩余 LLM 成本

当前使用本地 `qwen2.5:1.5b-instruct`，已经是较小模型。进一步缩小不保证在当前硬件上更快，也可能损害候选决策。

优先顺序：

1. 模型常驻，区分冷加载与稳态请求。
2. 一次调用、短结构化输出，移除向 prefer 纠正的调用路径。
3. 精简提示，测量输入 token 与处理时间。
4. 记录推理排队、CPU/GPU 使用与 HBase 资源争用。
5. 在固定开发协议下比较模型，联合考察合法率、选择 regret 和 E2E。

AIS 两条相似度查询的 LLM 约 0.9–1.1 秒，当前最突出的问题是额外准备。T-Drive 某些开发查询只有约 58–61 ms 的普查执行节省，而 LLM 超过一秒，在逐条调用并等待的约束下很难净胜。

门控可以避免坏执行，但无法收回已经支付的 LLM 成本。无候选时若仍要求每条调用，需允许紧凑的保留 CBO 决策；若跳过调用，必须另报为另一服务协议。

**期望收获：**在决策质量可接受的条件下进一步降低关键路径，而非为缩短单次调用牺牲更多执行收益。

## 10. 轻量测试与验收

### 10.1 逻辑验收

- 合法但不同于 prefer 的输出不会触发纠偏重试。
- 一次调用约束生效；超时/非法提议回退并保留原因。
- 未投机候选也能经过验证后正确执行。
- 已准备计划不会重复进入已确认可复用的准备阶段。
- 复用对象绑定语义和版本；快照/规则变化正确失效。
- 删除诊断成本卡不破坏执行、trace、汇总和决策依赖。
- 投机取消可观测，未结束任务不悄悄污染下一轮。
- Oracle 回归通过；不要求合法方法出现人为错查。
- 计时子区间不重复累加，真实 E2E 保留失败与清理语义。

### 10.2 分阶段开发验证

先只增加计时，确认结果与计划不变；再修改准备路径，保持模型协议不变，以隔离流程收益；之后单独改 LLM 协议，最后做校准和模型变化。

首要开发案例使用 AIS Fréchet 和 DTW，保留小查询与 T-Drive 对照。重复次数、顺序轮换、停止规则在跑次前固定，不根据是否刚好获胜提前停止。

串行/投机分别报告，不用完整规划加完整执行冒充投机墙钟。资源预算、缓存协议和 Oracle 口径一致。公共组件改变后重新测 CBO。

### 10.3 推进条件

进入下一阶段需要回答：

1. 主要耗时已定位到可解释子阶段吗？
2. 准备路径是否真正减少工作，而非仅改计时边界？
3. 计划安全和答案是否保持一致？
4. E2E 改善是否超过运行波动，并保留负结果？
5. 改善来自公共优化、候选扩展、排序校准还是 LLM？

准备耗时下降但仍未净胜是有效工程进展，不能写成实验胜出。若两条开发查询都无空间，不宜立即扩大到全量实验。

## 11. 泛化验证与全量目标

完成开发后冻结代码、配置、模型、提示和阈值，再确定新的小规模机制查询。可沿用约 12 条的规模，但它只能提供初步机制证据，不能精确估计总体胜率。

查询按事前声明的机制与种子生成，覆盖相似度/时空选择、不同范围与普通短查询；不依据 hybrid 运行胜负替换。若看完结果继续调参，这些查询转为开发集。

报告同一 query/trial 的 E2E 差值、胜平负、最差退化、总体耗时、失败率与资源成本。全量能否胜出取决于：

```text
长查询累计净收益 > 短查询累计额外开销 + 失败/回退成本
```

如果实际负载偏短，逐条等待 LLM 可能无法取得总体优势。应如实报告有效场景和边界；不能通过重新配权或删掉短查询制造全量胜出。预先声明的不同场景分层可以分别报告。

## 12. 建议交付物与最终预期

第二轮建议单独保存到 `docs/refine_2/` 或带版本的结果目录；以下产物尚未由本文件创建：

- `prepare_breakdown.md/jsonl`：编译、验证、特征与定位耗时，解释长等待来源。
- `prepare_reuse_review.md`：复用对象、版本约束、被消除工作与公平性范围。
- `paired_before_after.jsonl`：同协议下优化前后及新 CBO 基线的逐行结果。
- `llm_independent_decision.md`：去除强制 prefer 后的自主选择、回退和投机浪费。
- `calibration_validation.md`：数据分组、标签、误差与 holdout 结果；未完成则明确标记。
- `summary.md`：正确性、E2E、归因、退化场景及是否值得扩大验证。

本轮最重要的预期收获有三项：

1. 确认 AIS 已有执行优势能否通过减少额外准备转化为 E2E 净收益。
2. 确认 LLM 在不被强制服从 FastCost 后，是否产生真实决策增量。
3. 确定现有计划空间和逐条 LLM-on 条件下的可获益场景与不可覆盖的成本边界。

推荐立即开始的开发范围是：**分段计时 → 安全准备复用 → 取消强制 prefer 与纠偏重试**。先取得这三项的独立证据，再决定校准规模和模型调整，不预设结果必然超过 CBO。
