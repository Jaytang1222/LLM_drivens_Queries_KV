# 第六轮问题修复与第七轮开发迭代

日期：2026-10-01（Asia/Shanghai）。本目录保存开发迭代与重复确认，不能作为未知查询或全量论文结论。

## 最终结论

本轮已完成代码修复、服务器开发迭代及两轮冻结配置确认。最佳完整配置是 v11 + 在线配对收益校准 + 1.5B 模型的 2 线程/1024 上下文别名。没有按单条查询切换配置。

- 原生 CBO：plan **46.91 ms**、execute **975.54 ms**、真实 E2E **1022.44 ms**。
- 优化前（第六轮旧 jar 重跑）：plan **2617.63 ms**、execute **1609.19 ms**、真实 E2E **2806.26 ms**。
- 优化后：plan **666.93 ms**、execute **778.48 ms**、真实 E2E **990.78 ms**。

以上为全计时行算术平均；优化前 9×3 行，优化后及同跑 CBO 各 9×6 行。优化后比旧版观测 E2E 下降 **64.69%**；相对同跑 CBO 下降 **3.10%**。旧版时间块的同跑 CBO E2E 为 **1017.93 ms**，与新版本的 CBO 均值接近，但不能据此声称完全排除了环境影响。

**只在整个九查询等频工作负载的平均耗时上小幅获胜，不是多数查询获胜。** 两个独立时间块分别为 1007.26 对 1030.74 ms（快 2.28%）、974.30 对 1014.15 ms（快 3.93%）。合并后 2/9 查询胜出、12/54 配对 trial 胜出；其余 7 条各 6 次均落后。按每查询 E2E 中位数求比值再取几何平均，hybrid/CBO 仍为约 **2.17**，说明许多短查询的相对损失仍很大。

两条获胜查询均 6/6 次胜出，使用的是规则选出的 `P_T`，没有按查询 ID 硬编码：

- `ais_topk_dtw_2week`：CBO E2E 中位数 2724.5 ms，优化后 1658.5 ms；配对节省 765–1544 ms。
- `ais_topk_frechet_wide`：CBO E2E 中位数 2525 ms，优化后 1132.5 ms；配对节省 1087–1508 ms。

所有最终确认行 Oracle 均通过；每条 hybrid 查询均真实调用一次 LLM。逐查询三组 plan/execute/E2E 见 [results.md](results.md)，全部原始行保留在 `before/`、`after/`、`after2/`。`resource_trial/`、`resource_repeat/` 分别保留两轮单独汇总，`default_resource/` 保留资源限制前完整配置的负结果。

结论是：找到一个可重复的开发场景平均净收益配置，尚未解决多数查询的损失，也没有证明未知查询上稳定胜出或 LLM 独特价值。没有继续缩小风险余量去追求更多胜出。

## 改动

1. 移除旧探测路径按样本规模给预测节省增加最多 800 ms 的无依据奖励。探测目前仅作为诊断，没有宣称形成有效的联合选择率估计。
2. 对原普查中 P_T/P_Z/P_TZ 的候选对，重建执行前特征；以语义指纹核对测量，不使用执行后扫描计数作为在线输入。
3. 排除当前九条查询 ID，按查询分组比较线性与对数非负回归。最终指纹核对后的线性模型为 32 条查询、64 个候选对，经验上侧余量约 333.21 ms。仍是旧 T-Drive 开发数据上的模型，AIS 属于跨数据分布应用，不具有概率保证。
4. 新 v11 协议在投机前排除必然被门控拒绝的候选；模型只在可采纳列表和 KEEP 中选择，输出受 JSON Schema 枚举约束。空列表也真实调用模型，满足本轮逐条 LLM-on。
5. 固定一次调用、复用单请求内成本特征、保留完整安全验证、使用已有最多一个候选投机/KEEP 并行路径。
6. 修正模型版本和 llm_requested 记录。结构化解码仅对 v11 显式启用，旧调用不改变。

## 归因边界

此版本主要验证“校准 + 更短且合法的模型输出 + 调度”能否获得净收益。候选由校准器排序，LLM 常选择第一名；不能将实验改善解释为已经证明 LLM 超越确定性排序器。

不存在降低 CBO 性能的改动。服务器保留 target/kart.jar 和实验 before.jar；新类仅编入 experiments/refine_7/after.jar。新旧模型实验均计入真实调用与执行竞争。

训练排除了九条查询 ID，且核对训练语义指纹，但历史普查与当前工作负载包含相关查询族。这里不是严格的独立泛化评估。经验余量与历史开发性能也不能保证服务器当前运行时延。

## 已知限制

- 短查询仍要支付模型等待；全量获胜没有保证。
- 训练成本标签来自历史环境；统计快照哈希、源码和构建身份需随模型记录。
- 现有 warm 协议不是 OS cold 保证。
- 投机执行与规划重叠，字段中位数不可相加推导 E2E。
- 各版本在相邻时间块运行，保留其各自同跑 CBO 以检查基线漂移。
- 本轮余量是新模型的查询分组 OOF 残差 p90；第六轮使用约 1128 ms 的旧残差 p95。两者的数据、特征、分位点均不同，不能把余量下降直接解释为同等置信度下的提升。安全验证与 Oracle 不因性能门控余量变小而降低要求。
- 服务器仅有 4 个可用 CPU，且确认期间观察到其他 Spark 作业；本次均为共享服务器上的开发测量，不能把小幅均值差异直接解释为显著提升。

## 推理资源实验

使用 `scripts/create-refine7-resource-model.py` 创建独立 Ollama 别名 `kart-refine7-1p5b-t2`，继承原 `qwen2.5:1.5b-instruct` 权重，仅固定 `num_thread=2`、`num_ctx=1024`。API 回读已确认两个参数生效；未修改原模型或服务器服务配置。

此实验用于减少 LLM 与 HBase/客户端计算的 CPU 争用。单次规划快不代表查询总耗时一定快，所以仍比较完整九条查询及同跑 CBO，记录执行时间。这里同时修改线程与上下文，不能进一步分离两者各自的贡献。

原始资源配置对照：`after-20261001-222135`；资源限制首次确认：`after-20261001-223423`；保持配置不变的重复确认：`after-20261001-223756`。每个时间块每条查询 3 次，禁止挑选单条查询的较优时间块合并。
